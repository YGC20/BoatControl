- 생성자 `UdpReceiver(uint16_t port, int timeout_ms)`, 소멸자, `bool receive(dsu::DetectionPacket& out)`.
- 멤버는 POSIX `int sock_` (징크보드는 리눅스라 WinSock 분기 불필요 — vision의 `UdpSender`와 대칭되는 구조).

### `src/motor_controller_stub.cpp`
- `MotorControllerStub` : `apply()`에서 콘솔에 명령어 문자열만 출력. 실물 없이 로직 테스트용.
- 파일 끝에 `extern "C" MotorController* create_motor_controller() { return new MotorControllerStub(); }` — vision의 `create_detector()`와 동일한 팩토리 패턴.

### `src/motor_controller_gpio.cpp`
- `libgpiod` C API(`<gpiod.h>`) 사용.
- 생성자: `gpiod_chip_open_by_number(dsu::kGpioChip)` → 4개 핀 각각 `gpiod_chip_get_line()` + `gpiod_line_request_output(line, "boat_motor", 0)`.
- `apply()`: `gpiod_line_set_value(line, 0/1)` 조합으로 방향 결정. **`motor_control.py`의 `setIntegratedControl()`과 방향 조합을 동일하게 맞출 것** — LEFT/RIGHT는 "한쪽만 정지"가 아니라 "좌우를 서로 반대로 돌려 제자리 회전"하는 방식 (CH1=좌, CH2=우 기준: RIGHT=좌 FORWARD·우 BACKWARD, LEFT=그 반대).
- 소멸자: `apply(Stop)` 먼저 호출 후 `gpiod_line_release()` 각 라인 → `gpiod_chip_close()`.
- 에러 처리: `gpiod_chip_open`/`gpiod_line_request_output` 실패 시 예외(`std::runtime_error`)로 즉시 드러나게 — 배선/권한 문제를 조용히 넘기지 않도록.
- 파일 끝에 동일하게 `extern "C" MotorController* create_motor_controller()`.

### `src/distance_sensor.cpp`
- `DummyDistanceSensor(double fixed_cm)` : 고정값 리턴.
- `create_distance_sensor()`에서 100.0 반환 (항상 "장애물 없음" 취급). 실장착 시 `distance_sensor.py`의 trigger/echo 타이밍 로직을 GPIO(libgpiod) 버전으로 이식.

### `src/udp_receiver.cpp`
- `socket(AF_INET, SOCK_DGRAM, 0)` → **`setsockopt(SO_RCVTIMEO)` 반드시 설정** (없으면 `recvfrom`이 무한 블록되어 초음파 장애물 체크가 못 돎) → `bind(INADDR_ANY, port)`.
- `receive()`: `recvfrom` 리턴값이 `sizeof(DetectionPacket)`과 다르면(타임아웃 포함) `false`. 크기가 맞아도 `packet.magic != dsu::kDetectionPacketMagic`이면 버리고 `false`.

### `src/main.cpp`
1. `--port` CLI 파싱 (기본값 `dsu::kDefaultBoatPort`).
2. `SIGINT`/`SIGTERM` 핸들러 등록 — Ctrl+C나 SSH 세션 종료로 프로세스가 죽어도 루프를 빠져나가서 `motor->apply(Stop)` 호출 후 종료. 실물 모터가 돌아가는 상태로 연결이 끊기는 사고를 막기 위해 필수.
3. 제어 루프:
   - `distance->read_cm() < 20.0` → `Stop` & continue (`yolo_main.py`의 `MIN_DISTANCE=20`와 동일)
   - `receiver.receive(packet)` 실패 또는 `num_detections == 0` → `Right`(탐색 회전) & continue
   - `score` 최댓값 detection 1개 선택
   - `x_center = (x1+x2)/2`, `frame_center = frame_width/2` 비교, `TOLERANCE=80`(`yolo_main.py`와 동일) 이내면 `Forward`, 왼쪽이면 `Left`, 오른쪽이면 `Right`
4. 정렬/타겟 선택 로직은 vision이 아닌 boat 책임 (vision은 임계값 통과분을 그대로 넘김 — 기존 설계 유지).

## 🧩 5️⃣ GPIO 설정 관련 참고 (PS MIO vs PL)

| 방식 | Vivado 작업 | 비고 |
|---|---|---|
| PS GPIO (MIO 핀) — **채택** | Zynq PS 블록에서 MIO 핀 enable (가벼운 설정) | `/dev/gpiochip0`, `libgpiod`/`xgpiops`로 리눅스에서 바로 접근. 모터 on/off 제어에 충분 |
| PL GPIO (AXI GPIO IP) | 블록 디자인에 IP 추가 + 배선 + 비트스트림 재생성 | PS MIO 핀 부족하거나 PL 로직 연동 필요할 때만 |

- Vivado에서 MIO 핀 설정을 바꾸면 hardware description(`.xsa`) export → `petalinux-config --get-hw-description` → `petalinux-build`로 디바이스트리/커널 재생성 → SD카드(부팅 이미지) 갱신까지 한 세트로 따라옴. 즉 "Vivado만 하면 끝"이 아니라 PetaLinux 재빌드 + 재부팅 이미지 반영까지 필요.

### 초음파 센서 인터럽트 구조 설계 논의
현재 `distance_sensor.cpp`(더미)를 실장치로 교체할 때 폴링 대신 인터럽트 구조로 만드는 방법에 대해 논의, 아래와 같이 정리함 (구현은 아직 안 함):

- PetaLinux(유저스페이스)에서는 MCU의 EXTI ISR을 직접 쓸 수 없고, **libgpiod의 edge-event API**(`gpiod_line_request_both_edges_events` + `gpiod_line_event_wait`/`_read`)로 커널 GPIO 인터럽트를 이벤트 형태로 받는 것이 실질적인 "인터럽트 구조".
- 설계: Echo 라인을 edge-event로 요청 → 전용 백그라운드 스레드가 트리거 펄스 송신 → rising/falling 이벤트 대기(타임아웃 필수) → 이벤트의 커널 타임스탬프(`event.ts`)로 펄스 폭 계산 → 결과를 `std::atomic<double>`에 저장. `read_cm()`은 이 atomic 값을 즉시 반환(non-blocking)하도록 분리 — 메인 제어 루프가 측정 지연에 안 묶이게 됨.
- 트리거 펄스(10us)는 여전히 busy-wait 필요(인터럽트로 대체 불가 영역), edge-event wait는 반드시 짧은 timeout을 줘서 센서 무응답 시/소멸자 join 시 멈추지 않게 처리.
- `DistanceSensor` 인터페이스는 변경 없음 — `main.cpp`는 그대로 두고 구현체만 교체하는 구조.

### `boat/temp/` 커널 모듈 방식 검토
`boat/temp/testLed.c`(캐릭터 디바이스 커널 모듈) + `testled_1.c`(유저 앱) 실습 코드를 참고해, 이 방식으로 전환 가능한지 검토함.

- 이 방식은 `request_irq(gpio_to_irq(echo_pin), ...)`로 **진짜 ISR**을 등록해 `ktime_get()`으로 타임스탬프를 찍는 구조라, 개념적으로는 libgpiod edge-event 방식보다 "더 정확한" 인터럽트 구조.
- 다만 비용이 큼: PetaLinux 커널 소스 트리에 맞춘 별도 빌드(`KDIR`), `insmod`/`petalinux-create -t modules`로 rootfs에 편입해야 재부팅 후에도 유지, 레거시 GPIO 넘버링(전역 정수, base offset을 보드에서 직접 확인해야 함), ISR 작성 규칙(top-half는 non-blocking), 커널 패닉 위험 등 — report 1️⃣에서 "PL 방식은 무겁다"고 판단해 PS MIO+libgpiod로 가볍게 가기로 한 결정과 반대 방향의 복잡도 증가.
- 결론: **모터는 전환 난이도 낮음**(LED on/off와 동일 패턴), **초음파는 방향 자체는 적합하나 빌드/배포/디버깅 인프라 비용이 크게 늘어남** → 두 방식(libgpiod 스레드 vs 커널 모듈) 중 어느 쪽으로 갈지는 아직 미결정, 다음 목표(6️⃣-5)로 남김.
