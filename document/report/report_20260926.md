# 2026-09-26 작업 기록 — 실제 보드 부팅 & UDP 파이프라인 End-to-End 검증

## 오늘의 목표
SD카드를 실제 Zybo Z7-10 보드에 장착해 부팅시키고, 지금까지 준비해둔 소프트웨어 스택(커널 모듈, `boat` 앱, `vision` 앱, UDP 통신)이 실물 하드웨어에서 실제로 동작하는지 검증.

## 진행 내역 (시간 순)

### 1. 보드 부팅
- SD카드를 Zybo Z7-10에 장착, PROG/UART 마이크로USB로 노트북과 연결, 전원 인가.
- Digilent Adept USB(FT2232H)가 `/dev/ttyUSB0`(JTAG), `/dev/ttyUSB1`(UART) 두 채널로 인식됨.
- `sudo screen /dev/ttyUSB1 115200`으로 시리얼 콘솔 연결 → Dropbear SSH 키 생성, syslogd/klogd/tcf-agent 정상 기동 → **`root@Zybo-Z7-10:~#` 쉘 프롬프트까지 정상 도달**. 첫 실물 부팅 성공.

### 2. 시리얼 콘솔 → SSH(네트워크)로 전환
- 시리얼 콘솔이 인터랙티브하게 쓰기엔 너무 느려서(FTDI 레이턴시, Ctrl+S 오조작 등) SSH로 전환 결정.
- 노트북에 유선 랜포트가 없어 USB-이더넷 어댑터(`enx5414a7e48009`)로 보드-노트북 다이렉트 연결 (공유기 없음 → 양쪽 고정 IP 필요).
  - 노트북: `192.168.10.2/24` (기존에 설정되어 있던 값 재사용)
  - 보드: `ifconfig eth0 192.168.10.10 netmask 255.255.255.0 up`
- SSH 연결 시 두 가지 호환성 문제 발견 및 해결:
  - 최신 OpenSSH 클라이언트가 Dropbear(구버전)의 `ssh-rsa` 호스트키를 기본 거부 → `-o HostKeyAlgorithms=+ssh-rsa -o PubkeyAcceptedAlgorithms=+ssh-rsa` 옵션으로 해결
  - `scp`도 동일 이슈 + Dropbear에 `sftp-server`가 없어서 최신 scp 기본 프로토콜(SFTP) 실패 → `-O`(레거시 scp 프로토콜) 옵션 추가로 해결
- 이후 모든 작업을 SSH로 진행 (훨씬 쾌적함).

### 3. GPIO base 확인
- `cat /sys/kernel/debug/gpio` → 이 커널은 `CONFIG_DEBUG_FS`가 꺼져있어서 파일 자체가 없음.
- 대안: `/sys/class/gpio/gpiochip*/label`, `/base`로 확인 → `zynq_gpio` = `gpiochip905`, **base=905** (드라이버 코드의 기본값 905와 정확히 일치 확인).

### 4. 커널 모듈 로드
- `find / -name "*.ko"`로 확인 → `motor_driver.ko`, `echo_driver.ko`가 `/lib/modules/4.9.0-xilinx-v2017.4/extra/`에 이미 rootfs에 포함되어 있음 (이전 세션에 `petalinux-build`로 이미지에 들어가 있었음).
- `insmod motor_driver.ko gpio_base=905`, `insmod echo_driver.ko gpio_base=905` → 둘 다 에러 없이 로드 성공.
- `dmesg`: `motor_driver: 초기화 완료`, `echo_driver: 초기화 완료 (trigger=GPIO920, echo=GPIO919)` 확인. GPIO 핀 충돌 없음.
- `/dev/motor_driver`(244), `/dev/echo_driver`(243) 디바이스 노드 정상 생성 확인.

### 5. `boat_bin` 최초 실행 및 "먹통처럼 보인" 이슈 분석
- 이전 세션에 크로스컴파일해둔 `boat_bin`을 scp로 보드에 전송, `chmod +x`, 실행.
- 실행 후 프롬프트로 안 돌아오고 콘솔에 아무 출력도 없어서 처음엔 "센서 미연결로 인해 무한 블로킹"이라고 잘못 판단함.
- 소스 코드(`echo_driver.c`, `main.cpp`, `distance_sensor_dev.cpp`) 직접 리뷰로 정정:
  - `echo_driver.c`의 `echo_isr()`는 GPIO 인터럽트(rising+falling edge) 기반으로 펄스폭을 실제로 측정하는 구조가 맞음 (사용자가 질문으로 정확히 짚어낸 부분).
  - `echo_read()`는 `wait_event_interruptible_timeout(..., 40ms)`로 **40ms 타임아웃이 있어 무한 블로킹하지 않음**. 센서 미연결 시 타임아웃 → `-ETIMEDOUT` → 유저스페이스에서 999cm(장애물 없음)로 처리.
  - `main.cpp` 메인 루프는 순차적 단일 스레드 구조: 거리 체크(≤40ms) → 문제 없으면 `UdpReceiver::receive()`(≤200ms, 이게 실질적인 주 데이터 스트림 = 영상 탐지 결과) → 패킷 있으면 그 방향으로, 없으면 `returnDir()`(랜덤 방향)으로 폴백.
  - 즉 `boat_bin`은 실제로는 약 240ms 주기로 정상적으로 계속 돌면서, 영상 앱이 아직 안 떠 있어서 UDP 패킷이 없었기 때문에 **조용히 랜덤 방향 모터 명령을 계속 내리고 있었던 것**(콘솔 출력이 원래 없는 코드라 멈춘 것처럼 보였을 뿐). `Ctrl+C` 시 `echo_driver: release`, `motor_driver: release`가 깔끔하게 찍히며 정상 종료됨 — 크래시나 커널 패닉 없음, 드라이버/앱 스택 건전성 확인.

### 6. UDP 수신 확인용 디버그 로그 추가
- `main.cpp`의 `receiver.receive(packet)` 성공 시 `num_detections`/`frame` 정보를 stdout에 출력하는 디버그 라인 1개 임시 추가 (검증 목적, 필요시 제거 가능).
- 컨테이너에서 동일한 크로스컴파일 명령으로 재빌드 → scp로 보드에 재전송.

### 7. `vision` 앱을 노트북에서 네이티브 빌드
- `BoatControl_cpp/CMakeLists.txt`의 `BUILD_VISION`/`BUILD_BOAT` 옵션 확인, `-DBUILD_VISION=ON -DBUILD_BOAT=OFF`로 vision만 빌드 (크로스컴파일 아님, 호스트 네이티브, OpenCV만 필요, ONNX Runtime 없이 스텁 디텍터 사용 — 항상 탐지 0개 반환하지만 패킷 포맷/전송 경로 검증에는 충분).
- `./vision --host 192.168.10.10 --port 5555 --camera 0` 실행 → 노트북 카메라로 실시간 캡처 확인.

### 8. UDP End-to-End 검증 성공
- 보드 SSH 콘솔에 `[UDP] packet received: num_detections=0 frame=640x480 frame_id=...`가 실시간으로 계속 출력되는 것 확인.
- `frame_id`가 간헐적으로 누락되는 것 관찰(예: 435, 438, 441 등 스킵) → 카메라 프레임 주기(~33ms)가 보드 루프 주기(최소 40ms, 초음파 타임아웃 포함)보다 빨라서 커널 UDP 수신 버퍼에서 일부 유실되는 정상 현상으로 판단. 실시간 제어 특성상(최신값만 유효) 기능적으로 문제 없음.
- **결론: 카메라 캡처 → 탐지 패킷 생성 → UDP 전송 → 네트워크 → 보드 수신 → (모터 제어 분기)까지 전체 파이프라인이 실물 하드웨어에서 정상 작동함을 확인.**

## 오늘 확정/정정된 사실
- GPIO base = 905 (실측 확인, 코드 기본값과 일치)
- `echo_driver`는 인터럽트 기반 측정 + 40ms 타임아웃 있음 (무한 블로킹 아님) — 이전 세션 노트의 "무한 대기 가능성" 우려는 기우였음, 정정 완료.
- `boat`/`vision` 간 UDP 프로토콜(포트 5555, `bcc::DetectionPacket`, magic `0xD5C1`, 204바이트) 실물 검증 완료.
- 보드-노트북 네트워크는 공유기 없이 이더넷 다이렉트 + 고정 IP로 충분히 구성 가능함을 확인.
