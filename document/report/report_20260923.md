### `num_detections` 검증 버그 수정 — 완료
- `udp_receiver.cpp`의 `receive()`에 `if(packet.num_detections > bcc::kMaxDetections) { return false; }` 추가.
- 위치는 두 후보(receiver에서 거부 vs main에서 clamp) 중 **receiver 거부**를 선택 — "손상된 패킷은 신뢰 경계에서 폐기"가 원칙에 맞고, main에서 clamp하면 `num_detections=20`인데 실제 8개만 채워진 패킷을 그럴듯하게 처리해버리는 위험이 있음.
- 테스트 스크립트의 `num_over_8`, `num_max` 케이스를 관찰(`INFO`)에서 `expect_ignored_not("Left")` 기반 PASS/FAIL 판정으로 전환.
- 재빌드 후 테스트: PASS 16 / FAIL 0 / INFO 1 (`oversize`만 남음). `num_max`(과거 SIGSEGV)가 크래시 없이 랜덤 탐색으로 처리되는 것까지 확인.

### `oversize` 데이터그램 처리 — 완료
- 원인: UDP는 `recvfrom` 버퍼보다 큰 데이터그램이 와도 조용히 잘라 받고, 반환값(`n`)은 버퍼 크기만큼만 나와서 "정상 204바이트"와 "잘린 300바이트"를 구분 못 함.
- 해결: `recvfrom`의 flags를 `0` → `MSG_TRUNC`로 변경. Linux에서 이 플래그를 쓰면 반환값이 **실제 데이터그램 전체 크기**가 되어, 기존 길이 비교(`n != sizeof(packet)`)가 자동으로 걸러줌.
- 해프닝: 첫 테스트에서 재빌드를 안 하고 돌려서 "여전히 Left로 수락됨"으로 오인 — 바이너리 타임스탬프가 소스 수정 시각보다 이전임을 확인하고 재빌드 후 재검증.
- `oversize` 케이스도 PASS/FAIL 판정으로 전환 → **전체 PASS 17 / FAIL 0 / INFO 0**.

## 📦 3️⃣ 확인된 기술 사실

- 이 PC(Ubuntu)의 apt `libgpiod-dev`는 **v2.2.1만 후보**(v1 없음). **타깃 PetaLinux BSP의 libgpiod 버전은 아직 미확인** — 다를 수 있음(다음 단계에서 반드시 확인 필요).
- libgpiod v2 API는 v1과 완전히 다른 객체 모델: v1은 `chip`에서 `line`을 바로 얻어 조작, v2는 `line_settings`(설정) → `line_config`(핀에 설정 매핑) → `request_config`(선택, consumer 이름 등) → `gpiod_chip_request_lines()`로 `line_request` 획득 → 그걸로 값 읽기/쓰기.
- `recvfrom`에 `MSG_TRUNC` 플래그를 주면 버퍼보다 큰 UDP 데이터그램이 와도 반환값이 **버퍼 크기가 아니라 실제 데이터그램 전체 크기**가 됨 (Linux 전용 동작).
- Zynq-7000(Cortex-A9, 32비트 ARM)에서 `s64`/`ktime_t`(64비트) 값의 읽기/쓰기는 **원자적이지 않음** — 하드 IRQ와 프로세스 컨텍스트가 락 없이 공유하면 torn read 위험이 실재함.
- 커널 모듈 `Makefile`의 `KDIR`은 PetaLinux 빌드 결과물 안의 커널 빌드 트리를 가리켜야 하는데, **아직 실제 경로를 모름** (PetaLinux 빌드 후 확정).
- 이 PC엔 크로스 툴체인(`arm-linux-gnueabihf-gcc` 등)이 없음 — PetaLinux SDK 설치가 선행되어야 함.
